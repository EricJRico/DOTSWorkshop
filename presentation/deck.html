Jobs · The idea Loops

Same work. Split across the cores you already own.

IJobParallelFor runs the same Execute once per index, on whichever core is free. You never write a thread.

Jobs · Handing it over Loops

Schedule now. Wait later.

Schedule hands the work over and returns straight away. Complete is where you wait — and you only wait when you actually need the results.

Call it on the very next line and you waited for nothing. You could also never wait at all, and hand the handle to next frame’s job instead. Today we do need them: the positions go back onto the transforms this frame.

Jobs · The shape of it

The loop you know, turned inside out.

What you write today
public class Enemy : MonoBehaviour { public float Speed; void Update() { Vector3 dir = (_target.position - transform.position).normalized; transform.position += dir * Speed * Time.deltaTime; } }

One call per enemy, on the main thread. It reads transform — a managed object.

The same work, as a job
[BurstCompile] struct MoveEnemiesJob : IJobParallelFor { public float3 Target; public float Speed, DeltaTime; public NativeArray<float3> Positions; public void Execute(int i) { float3 dir = math.normalize(Target - Positions[i]); Positions[i] += dir * Speed * DeltaTime; } }

One call per index, on any core. NativeArray because a job cannot touch a managed object.

job.Schedule(Positions.Length, 64) hands it over · handle.Complete() waits for it back.

Entities · The vocabulary

ECS means entity, component, system.

Entity
An id. It holds no data and no code. It identifies a thing; it is not the thing.
Component
A piece of plain data, attached to an entity. A position, a speed, a radius. No behaviour on it.
System
Code that runs over every entity carrying a given set of components.

A MonoBehaviour is all three at once: identity, data and behaviour in one class. ECS separates them, and every difference for the rest of the day follows from that.

Entities · The entity

An entity is an id and nothing else.

Unity.Entities · Entity.cs
public struct Entity { public int Index; public int Version; }

That is the whole thing. No position, no speed, no health.

Index
Which entity it is.
Version
Raised when an entity is destroyed, so an id you kept from a dead one does not point at whatever reused the slot.
A struct
Two ints. Nothing allocated, nothing for the garbage collector to track.

A MonoBehaviour arrives with a GameObject, a Transform, an enabled flag and message plumbing, used or not. An entity carries only what you put on it.

Entities · The component

A component is a struct of data on an entity.

Workshop · WorkshopComponents.cs
public struct EnemyTag : IComponentData { } public struct MoveSpeed : IComponentData { public float Value; } public struct Radius : IComponentData { public float Value; }
IComponentData
The interface that lets a struct be put on an entity. No base class, no methods, nothing to override.
A tag
EnemyTag has no fields. It stores nothing; it only lets code ask which entities are enemies.
Unmanaged
No references to managed objects. That is what lets a component live in native memory and be read by Burst-compiled code.

Position is a component as well: LocalTransform, added for you during baking. There is no separate transform object to reach through.

Entities · How they are stored Loops

An archetype is the exact set of components an entity has.

Entities with the same archetype are stored together in a chunk: one block of memory, one array per component type. The packed layout from this morning.

Adding or removing a component changes the archetype, so the entity is copied to a different chunk. That is a structural change, and the last lab today is about avoiding it.

Entities · Where they come from

Entities are made by baking, and baking only runs in a subscene.

Subscene
A scene nested inside another one, marked for baking. Its contents become entity data.
Baking
The conversion, run in the editor while you work, not at load time.
In a normal scene

Stays a GameObject

It loads as a GameObject and runs as a GameObject. Nothing is converted.

The Baker never runs. No error, no warning, no entity.

In a subscene

Becomes an entity

Unity bakes it in the editor and writes out entity data. At runtime that data loads and no GameObject is made.

This is where authoring goes. Open it to edit, close it to see what ships.

When your lab does nothing at all, check this before you read your code.

Entities · The Baker

One class you fill in, one method that converts it.

Workshop · EnemyAuthoring.cs
public class EnemyAuthoring : MonoBehaviour { public float MoveSpeed = 2.5f; public float Radius = 0.5f; class Baker : Baker<EnemyAuthoring> { public override void Bake(EnemyAuthoring authoring) { var entity = GetEntity(TransformUsageFlags.Dynamic); AddComponent<EnemyTag>(entity); AddComponent(entity, new MoveSpeed { Value = authoring.MoveSpeed }); AddComponent(entity, new Radius { Value = authoring.Radius }); } } }
The class
A MonoBehaviour, so you get an Inspector. It exists in the editor only.
GetEntity
The entity this GameObject becomes. Dynamic asks for a LocalTransform, because this one moves.
AddComponent
Copies an authored value onto the entity. Read from authoring, write onto entity.
